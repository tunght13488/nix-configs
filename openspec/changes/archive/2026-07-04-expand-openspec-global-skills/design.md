## Context

The repo currently deploys 5 OpenSpec workflows globally via `home-manager/openspec.nix` using files checked into `pkgs/openspec-agent-files/`. These files were generated by `openspec init --tools pi,opencode --force` at some point, but only a subset of the OpenSpec workflows were included. The project's own `.pi/skills/` directory has all 11 workflow skills (generated by a more recent `openspec init`), confirming the CLI produces them — they just weren't copied into the global deployment package.

The global deployment targets two agents:
- **Pi**: `~/.pi/agent/skills/` (skills) and `~/.pi/agent/prompts/` (prompts)
- **OpenCode**: `~/.config/opencode/skills/` (skills) and `~/.config/opencode/commands/` (commands)

Each agent directory gets per-file links via `home.file` / `xdg.configFile` to coexist with other globally installed skills.

## Goals / Non-Goals

**Goals:**
- Deploy all 11 OpenSpec workflow skills as global agent skills for both Pi and OpenCode
- Deploy corresponding prompts (Pi) and commands (OpenCode) for all 11 workflows
- Keep the existing per-file linking approach so non-OpenSpec global skills aren't clobbered

**Non-Goals:**
- Changing the mechanism (Nix derivation + home-manager links) — this works fine
- Adding skills for OpenSpec commands outside the experimental workflow (e.g., `init`, `validate`, `schema`) — those are separate
- Automating regeneration of files from `openspec init` — out of scope; the spec already documents the manual regeneration process

## Decisions

### Decision 1: Regenerate all files from `openspec init`

The single source of truth for skill, prompt, and command files is `openspec init --tools pi,opencode --force`. Run this in a temp directory to generate the full set of 11 workflow files (skills, Pi prompts, OpenCode commands), then replace the entire contents of `pkgs/openspec-agent-files/` with the output. This ensures all files match what the installed CLI produces, including any fixes or improvements in newer OpenSpec versions.

**Alternatives considered:**
- Copy only missing 6 from `.pi/skills/`: risks drift between the 5 existing files and 6 copied ones if `.pi/skills/` was generated by a different CLI version.
- Manually write prompt/command files: error-prone and defeats the purpose of having the CLI as the generator.

### Decision 3: Keep per-file linking in home-manager module

Continue the existing pattern of individual `home.file` / `xdg.configFile` entries for each skill, prompt, and command. This preserves other globally installed skills in the same directories. Add entries for the 6 new workflows alongside the existing 5.

### Decision 2: Remove project-local OpenSpec skills after global setup

Once all 11 workflows are deployed globally via home-manager, the project-local `.pi/skills/openspec-*` directories are redundant. Remove them so the global skills become the sole source. This avoids confusion from duplicate skill listings and ensures the global version is always used.

## Risks / Trade-offs

- [Full regeneration touches existing 5] → Replacing all files at once means the existing 5 skill/prompt/command files get overwritten. Mitigation: run `git diff` after copying to verify only expected additions/changes; the CLI output should be identical or improved.
- [Removing project-local skills] → Projects that don't have home-manager active won't have OpenSpec skills. Mitigation: this is expected — the global deployment is the intended path. Individual projects can still run `openspec init` if they need local copies.
